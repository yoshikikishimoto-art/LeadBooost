TalentFlow
人材紹介 進捗・売上管理システム

集客（TimeRex予約・リファラル）から、着座・面談・企業提案・選考・内定・入社、そして売上の読み・確定・請求・入金までを一気通貫で管理する、CA／PCA事業のための業務基盤。

対象システムakanuma-webapp（TalentFlow）
版現状リバースエンジニアリング版
作成日2026-07-05
目的再要件定義に向けた現状の棚卸し
01背景と目的

なぜこのシステムか

人材紹介では、候補者の「進捗」と、そこに紐づく「売上・請求」が別々の道具（スプレッドシート・カレンダー・LINE）に散らばりがちで、着座率や売上の読みが即座に見えない。本システムは、候補者フローと売上を一枚の画面に統合し、CAは自分の担当を、マネージャー層は全体を、同じデータで見ることを狙う。

一気通貫

流入から入社・返金規定クリア、さらに請求・入金までを分断せず1本のフローで追う。

着座率の可視化

「予約」と「着座」を分離し、No-show（未着座）を数字で捉える。

売上の読み

選考ステータス別の確度で期待売上を算出し、目標対比で着地を予測する。

スコープに関する重要な注記
現行の README は「進捗管理 MVP」を謳っているが、実装は売上計上・請求ステータス・企業マスタ・リファラル獲得管理・確度別の売上読みまで踏み込んでおり、ドキュメントが実態に追いついていない。この乖離の解消（＝スコープの再定義）が「一から整理」の出発点になる。
02利用者と権限

4つのロール

全体を見るチーム層と、自分の担当だけを精査するCAを、同じデータの上で権限分離する。

ロール見える範囲主な用途
管理者（Admin）全データ ＋ 設定系（同期設定・データ取込／初期化）システム管理
マネージャーチーム全体の売上・進捗（閲覧）全体把握
サブマネージャーチーム全体の売上・進捗（閲覧）全体把握
CA（担当）自分が担当する候補者のみ自分の案件の精査
現状の制約
ログインは「開発モード：どのアカウントでもログイン可」＝本物の認証はなく、ロール権限は表示上の絞り込みに留まる。本番化では認証基盤の導入が前提。
03コア業務フロー

候補者ステージ

流入した候補者は次の10ステージを進む。予約と着座を分離し、辞退・未着座は「終了」へ分岐する。

※ 内定承諾以上＝売上計上（確定）の対象。承諾・入社を濃色で表示。

リファラル獲得の独自ステージ

リファラルは面談設定前に固有の獲得ステータスで管理する ― サスペクト → アクション済 → 承諾 → お繋ぎ済 ／ 不承諾。 紹介者（referrer）単位で「紹介数／面談化／入社」を集計する。

04機能要件

画面と主な機能

11の画面で構成される。左が集客〜進捗、右が売上〜マスタという役割分担。

画面主な機能
ダッシュボード稼働中候補者数・着座率・承諾率・今月入社などのKPI、ステージ別ファネル、流入経路内訳、最近の動き
面談カレンダー月／週表示、担当者カラー、予約 → 着座（着座マーク）操作
リファラル管理獲得ステータス管理、紹介者別の実績集計、「紹介宝箱」マスタ（チャネル・業種・職種・勤務地・学歴）
パイプラインカンバンでステージをD&D移動＋報告ボタン（提案企業一覧／応諾／エントリー／承諾／辞退／退社）
求職者一覧名前・企業・スキル検索、ステージ／流入／担当で絞込、CSV出力
求職者詳細希望条件・スキル、選考企業（1候補者に複数社）、活動履歴タイムライン
読み票（売上予測）選考ステータス別の確度%（提案5% … 内定70% … 承諾100%）で期待売上を算出
売上管理月次で セグメント別（CA／PCA／PCAシェア）・担当別・企業別の実績、目標対比、請求ステータス管理、決済テーブル、CSV出力
企業マスタ固定フィー or 料率×想定年収、税率、備考
アドバイザー管理担当件数・入社実績、担当の引き継ぎ（handoff）
データ連携TimeRex同期（GoogleスプレッドシートのCSV取込）／売上シートのJSON取込

売上・請求のステータス遷移

請求は 未請求 → 発行済 → 送付済 → 入金済（例外：返金） で管理し、承諾月・請求月・支払期日（翌月末想定）を保持する。

06非機能要件・技術構成

現状のアーキテクチャ

フロントエンド

ビルド不要の静的SPA。HTML / CSS / バニラJS の3ファイル（app.js 約2,470行）。CSS変数によるセマンティックデザイントークンで色・余白・角丸を単一管理。

データ保存

ブラウザの localStorage のみ（キー talentflow.db.v3）。サーバ・DBなし。

外部連携

Googleスプレッドシート経由（gviz CSV／JSON）で TimeRex 予約・売上シートを取込。正式なAPI連携ではない。

入出力

各画面から CSV エクスポート。JSONインポートでの一括投入に対応。

07再要件定義に向けた論点

本番化で決めるべきこと

現状は「動くプロトタイプ」として完成度が高い一方、複数人での実運用には次の5点の意思決定が必要になる。

  1. データの置き場所localStorage はブラウザ内に閉じるため、複数人・複数端末でデータを共有できない。本番はバックエンド／DBが必須。
  2. 認証と権限現状は「開発モード」で誰でもログイン可。ロール権限を実効化するには認証基盤（誰が・何を見られるか）の設計が必要。
  3. スコープの再定義README（進捗管理MVP）と実装（売上・請求まで）の乖離を解消し、「どこまでを本プロダクトの責務にするか」を確定する。
  4. TimeRex連携の正式化スプレッドシート手動経由を、API連携・自動同期へ引き上げるかを判断する。
  5. 売上ロジックのマスタ化確度%・返金規定・PCAシェアなどがコードにハードコードされている。運用で変更できるようマスタ化・設定化するか。
